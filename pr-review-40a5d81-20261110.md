## Executive summary

**Files changed:** 17 · **Findings after dedup and validation:** 27
(0 critical, 4 high, 11 medium, 12 low) · reviewer raw findings: 43, 0 rejected as false, the rest merged.

The VM design is sound: one fresh VM per job, JIT runner registration, no secrets baked into the
image, no host directory shared, softnet isolation, SHA-pinned actions, Asana token kept off GitHub.
The weak points are around it:

1. Asana task content (including colleagues' names) is printed in **public** Actions logs.
2. Anyone who can write to the Asana board can start a run with repo write access. The author is never checked.
3. Nothing technical stops Claude from merging its own PR into `staging`. From there its code runs with Staging secrets and migrations run as `postgres`.
4. The golden-image build VM has no network isolation and executes `staging` content. Combined with 3, a prompt injection can persist in the runner image and reach the LAN.

## High priority issues

### H1. Asana task content is published in public Actions logs
`.github/workflows/claude-asana.yml:41-46`, `infra/claude-runner/asana-listener.mts:149-180, 219`
**Actionability:** 8/10 · **Confidence:** high

The listener sends task title, description, all comments and commenter names as the
`context_b64` input. The workflow maps it to a step `env:`, and the runner prints step env values
in the log header. Base64 is not protection. The task URL is also printed (`with: prompt`), and
`reply.md` is a downloadable artifact for 3 days. The README warns only about the Claude API.
Colleagues' names in public logs are personal data under the TSB rules.

**Solutions**
1. **Encrypt the context (recommended).** Listener encrypts with a key that the workflow holds as an environment secret; the log then shows ciphertext only. Small effort. Do the same for the reply, or have the listener delete the artifact after download.
2. **Send less.** Drop `created_by.name`, send only the triggering comment plus description. Trivial, but the content stays public.
3. **Document and accept.** State in the README that the board content becomes public. Only acceptable if the board never holds internal content.

### H2. No authorisation on the Asana trigger
`infra/claude-runner/asana-listener.mts:118-147`
**Actionability:** 8/10 · **Confidence:** high

`findTriggers` never looks at who wrote the comment or edited the description. Board write access
equals "start Claude with repo write access and the API key". That can include guests, a public
form on the project, email-to-project, rules and integrations. README line 77
("only OWNER/MEMBER/COLLABORATOR") is not true for this path.

**Solutions**
1. **Allowlist of Asana user GIDs (recommended).** Asana events carry the acting `user`; reject anything not in a configured list, for both comment and description triggers. Small.
2. **Comment triggers only.** Drop the description trigger (it has no reliable author and re-runs on every edit, see M6) and check `created_by.gid` on the story. Small.

### H3. Claude can land code in `staging` without a human
`.github/workflows/claude.yml:31-36, 69-71`, `claude-asana.yml:59-75`
**Actionability:** 7/10 · **Confidence:** high for the chain, **(verify)** for App-token behaviour

`Bash(gh:*)` and `Bash(git:*)` plus contents: write allow `gh pr merge`. `staging` requires a PR
and 15 status checks but 0 approvals (ruleset 25967573, checked 2026-11-10). After a merge:
- `backend-deploy-stackit-cf.yml` deploys to Staging with the environment's 1Password token.
- `cleanup-*-orphans.yml` runs `npm run s3:assess-orphans` (repo code) next to the fetched staging backend env.
- `supabase-migrations.yml` applies any new migration as `postgres` on the staging database.
- If K5 is still open, the Staging 1Password token also reads production items.

The only guard is the sentence "Never push to main or staging" in the Asana prompt. `claude.yml`
has no such sentence, and a prompt is not a control against injected instructions.

You decided in October that `staging` needs no review because only the team has write access.
This PR adds a writer that issue text and Asana text can steer, so that premise changes.

**Solutions**
1. **Ruleset that keeps the bots out of `staging` and `main` (recommended).** "Restrict updates" with the team on the bypass list. Humans keep the current no-review flow; `claude[bot]` and `github-actions[bot]` can only open PRs. Small, no code change.
2. **Reduce the token.** `contents: read` on `GITHUB_TOKEN` and `persist-credentials: false` on checkout, so only the App token can write **(verify the action still works)**. Trivial, complements 1.
3. **Close K5 first.** Limits the blast radius to staging regardless of what merges.

### H4. Golden build VM is not isolated and executes `staging` content
`infra/claude-runner/build-golden.sh:38, 47-50`, `golden/provision.sh:55-56, 80-85`
**Actionability:** 9/10 · **Confidence:** high

The build VM starts without `$VM_NET_FLAGS`, so it is on shared NAT with host and LAN reachable.
Inside it run `npm ci` lifecycle scripts of the `staging` checkout, `npx playwright` under sudo,
and version strings from `staging` files that are pasted unquoted into the remote shell
(`.nvmrc` → `NODE_VERSION=…`). Whatever runs there is baked into every job VM until the next
rebuild. With H3, the path is: injected instruction → change on `staging` → nightly build →
code on the office LAN and in all later jobs. No repo value is evaluated by a host shell; that
part is fine.

**Solutions**
1. **Start the build VM with `$VM_NET_FLAGS` too (recommended).** The host already reaches softnet VMs over SSH. Trivial.
2. **Validate versions on the host** against a strict pattern (digits and dots) before use, and quote them. Small.
3. **Keep relying on the existing install-script allowlist.** The repo pins npm 11.16.0 with `strict-allow-scripts=true` and `allowScripts` in `package.json`, so dependency install scripts are already limited. What remains is that `package.json`, `allowScripts` and `.npmrc` themselves come from `staging`; solutions 1 and 2 plus the H3 ruleset cover that. Building from `main` (`WARM_BRANCH=main`) is a further option, at the cost of more lockfile mismatches.

## Medium priority

**M1. Every job credential is readable by the agent** (`claude.yml:63`, both workflows) **(verify)**
`ANTHROPIC_API_KEY`, both GitHub tokens and the OIDC request variables sit in a process that
reads outsider text and has open egress. Inherent to the design. Mitigate: workspace-scoped API
key with a spend limit, `persist-credentials: false`, and check that no cloud trust policy accepts
`repo:technologiestiftung/baergpt:ref:refs/heads/main` without a workflow or environment condition.

**M2. PR-ref triggers block the two strongest hardening options** (`claude.yml:8-11`, README:25)
`pull_request_review` and `pull_request_review_comment` take the workflow from the PR ref. So the
runner group cannot be pinned to `claude.yml@main`, the API key cannot live in a branch-restricted
environment, and a fork PR can target the runner labels, held back only by the fork-approval
setting. Dropping these two triggers (people use the PR conversation instead of inline review
comments) allows both pins. Trade-off is yours; at minimum keep the approval setting on
"all external contributors".

**M3. Fork check fails open** (`claude.yml:44-49`)
If `gh pr view` fails, the output is empty, the comparison is false, the job continues. Compare
against `false` and fail on anything else. Trivial.

**M4. Runner App key gains Actions read/write** (README:65, 81-82; `asana-listener.mts:186-196`)
With the Asana setup, a stolen key can dispatch `backend-deploy`, `supabase-migrations` and the
cleanup workflows, approve fork PR runs and delete logs. Any process of the Mac user can read the
key from the keychain. Options: a second App used only for dispatch, and request down-scoped
installation tokens (single repo, single permission). README lines 29, 34 and 81 still describe the old scope.

**M5. Asana personal access token** (`config.sh:26`, README:66-69) **(verify)**
A PAT covers everything that person can see in Asana, and replies appear under their name. Use a
dedicated bot user that is a member of this one board.

**M6. Unbounded runs and cost** (`asana-listener.mts:290-296, 134-144`; `claude-asana.yml`)
One dispatch per trigger, no cap, no concurrency group, up to 60 min each. A description containing
`@claude` starts a new run on every later edit. The listener stops waiting after 75 min but does
not cancel the run. Add a cap in the listener and cancel on timeout.

**M7. Runner loop can hang or spin** (`runner-loop.sh:57-66`)
`( set -e … ) || log` disables errexit inside the subshell. If `tart ip` fails, the `until ssh`
loop never ends and the slot is dead. If JIT registration fails, the loop clones and deletes VMs
without backoff. There is also no upper bound on a VM's lifetime.

**M8. Stale build lock stops nightly rebuilds** (`build-golden.sh:10-13`)
After a kill or reboot the lock directory stays and every later build exits with "Another build
is running". The image then silently ages past the 7-day patch window.

**M9. Supply chain of the golden image** (`config.sh:6`, `provision.sh:40-68`)
Mutable base image tag, tarballs without checksums, `curl | bash` for bun and Claude Code. Pin the
base image by digest and verify checksums for at least the runner and Node. Also confirm
`openai/tools` is the official tap for tart and softnet, since softnet gets the SUID bit **(verify)**.

**M10. Bot approval on `main`** **(verify)**
Mostly resolved on 2026-11-10: `can_approve_pull_request_reviews` is `false`, so
`github-actions[bot]` cannot approve and Claude cannot approve its own PR. Still open: whether an
approving review by `claude[bot]` on a human-authored PR (for example the staging → main release
PR) counts toward the 1-approval rule on `main`. Three of the required checks are Vercel preview
deployments, so a Claude branch also gets built by Vercel; check which environment variables
preview builds receive.

**M11. Lost events and replies** (`asana-listener.mts:96-114, 267-286`)
The sync token advances before lookups succeed, so one 404 or 429 in `findTriggers` drops the
whole batch. A listener restart during a run loses the reply while the run continues.

## Architecture observations

- **The real trust boundary is the repo's rulesets, not the prompt or the tool allowlist.** Treat the agent as an untrusted contributor with write access and let rulesets, environments and the runner group decide what it can reach.
- **Two entry points, two authorisation models.** GitHub checks `author_association`; Asana checks nothing. One shared rule ("who may ask Claude to change code") should apply to both.
- **README security section lags the code** once Asana is on (lines 29, 34, 73, 77, 81-82) and omits the build VM.

## Positive observations

- Ephemeral VM per job, JIT registration, VM deleted afterwards.
- No secrets in the golden image; no host mounts; password login disabled after build.
- All third-party actions pinned to commit SHAs.
- `author_association` gate fails closed; explicit fork PR refusal.
- Asana token never leaves the Mac; artifact handled safely (`unzip -p` of one member, `execFile`, no shell).
- Dispatched run matched by random UUID; bot prefix prevents self-trigger loops.
- No repo-derived value reaches a host shell evaluation.
