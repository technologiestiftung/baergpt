# Schemas

The schemas are **declarative**: they reflect the desired state of the `public`
schema. The schemas `auth` and `storage` can't be included yet (see [Gotchas](#gotchas)). Migrations are generated by
diffing these files against the database.

## Making a change

1. Edit the relevant file(s) here.
2. Run `npm run db:generate-migration <MIGRATION_NAME>`: this diffs the
   schema and writes `migrations/<DATETIME>_<MIGRATION_NAME>.sql`.
3. Verify it's complete: `supabase db reset && supabase db diff --schema public` should print
   **no** diff. A leftover diff means something isn't captured.

## Load order

`config.toml` loads these files via `schema_paths = ["./schemas/**/*.sql"]`,
which expands **lexicographically**. The numeric prefixes are what enforce
order — always number a new file/folder into the correct slot.

Order matters because objects depend on each other:

| Prefix          | Contents                                                        | Why here                                                                                                                |
| --------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `00_extensions` | `CREATE EXTENSION`                                              | everything may depend on them                                                                                           |
| `01_settings`   | session `SET`s (pg_dump preamble)                               | sets `check_function_bodies = FALSE`, which lets functions load before the tables they reference                        |
| `02_schema`     | `public` schema creation, ownership, grants, default privileges | before any object in it                                                                                                 |
| `03_functions`  | functions                                                       | **before tables** — RLS policies call them (e.g. `is_application_admin()`); safe because `check_function_bodies` is off |
| `04_tables`     | tables + FKs + RLS policies                                     | after functions; individual tables are ordered **parent-before-child** for FKs                                          |
| `05_triggers`   | triggers                                                        | last — need both tables and functions to exist                                                                          |
| `99_orphaned`   | anything not yet sorted                                         | —                                                                                                                       |

Within `04_tables`, related tables share one domain file with the parent
defined first (e.g. `access_groups` before `access_group_members`).

## Table-file convention

Each table file is organized with section delimiters:

```sql
-- TABLE          -- create, owner, identity, pkey/unique, indexes
-- FOREIGN KEYS   -- ADD CONSTRAINT ... FOREIGN KEY (omit if none)
-- RLS POLICIES   -- ENABLE ROW LEVEL SECURITY + CREATE POLICY
-- (trailing GRANT/REVOKE)
```

## Gotchas

- **Only `public` is diffable.** Objects in `auth.*` and `storage.*` (e.g.
  triggers on `auth.users`, policies on `storage.objects`) are **not** picked up
  by declarative diff. Maintain those as hand-written migrations.
- **No nested `DO $$ … $$` inside a plpgsql function.** Function bodies are
  compared as opaque strings; nested dollar-quoting never round-trips and
  produces a perpetual no-op diff. Inline the logic into the function's own
  `BEGIN … END` block instead.
